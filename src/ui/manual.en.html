ApkStart User Manual and Troubleshooting Guide

Version: v0.6.4 · Platform: Windows 10/11 x64 · Updated: 2026-11-22 ApkStart is an Android app runner for Windows: install Android apps, see them on your desktop and open them with a double-click, just like native Windows software. This manual first shows you how to use it, then gives step-by-step fixes organized by "symptom". Every step refers to buttons and menus that actually exist in the app.

1. ApkStart in 30 seconds

Desktop shortcut (the real app icon, a .lnk)
      │ double-click
      ▼
ApkStart.exe --launch <package name>
      │ Android runtime not running? → started automatically (Android 14 emulator, bundled or downloaded on first run)
      ▼
Opens the app through the launch entry resolved by the system (not the main Activity hard-coded in the APK)
      ▼
Emulator window = app window (custom title, icon, portrait ratio, fullscreen and centered)

What it offers

  • 🖱️ Double-click an .apk to install: after you register the file association, double-clicking an APK in File Explorer parses it, installs it and creates a desktop shortcut.
  • 🧩 One desktop icon per app: the icon is extracted offline from inside the APK, and double-clicking it opens the app directly.
  • 🪟 The app is just a window: natively rendered, fullscreen fills the screen height and is centered, windowed mode can be dragged and resized, and each app remembers its own size.
  • 🔍 Searchable from Windows: two shortcuts, one on the desktop and one in the Start menu (Programs\ApkStart\).
  • 📁 Shared data: %USERPROFILE%\ApkStartShared ↔ /sdcard/ApkStartShared inside Android, synchronized in both directions.
  • 🪶 Bundled runtime: does not depend on MuMu, LDPlayer, WSA or any other emulator installed on your machine.
Note: this project is an early release, maintained by the author in spare time. It is open source, free and ad-free. Running into problems is normal, and this manual exists for that.

2. Installation and first launch

2.1 Choose the right edition

Both sources have identical content. Users in China should prefer Gitee:

  • GitHub: github.com/RoutineMiku/apkstart/releases
  • Gitee: gitee.com/daily-miku/apkstart/releases (much faster direct connection within China)
EditionFile nameWhen to choose it
Store editionApkStart_<four-part version>_x64.msixInstall from the Microsoft Store. Includes the complete runtime, needs no network after installation, and updates are handled by the Store
Full portable editionApkStart-v*-win64-full.zip (about 830 MB, ~1.3 GB unpacked)You do not want to install it or wait for downloads: unpack and run, the whole runtime is in the package
Installer editionApkStart-v*-Setup.exe (about 1.3 GB)You want desktop and Start menu shortcuts and an uninstall entry
Lightweight portable editionApkStart-v*-win64-portable.zip (96 MiB, ~227 MB unpacked)You just want to try it first; the runtime is downloaded on first launch
⚠️ Always use the latest version (currently 0.6.4). Older versions (0.5.x and earlier) either had no bundled runtime and looked for or downloaded a 1.5 GB runtime on every launch, or used the embedded window by default. That is the typical source of "very slow, will not open, a window with a rotate button appears". If you upgraded from an older version, make sure the desktop shortcuts point to the new program folder.

2.2 What happens on first launch

  1. (New installations) Choose the interface language: a language picker appears the first time you open the app. Choose Chinese, English, Russian, Vietnamese, Spanish, Portuguese, Japanese or Korean, or follow the system language. The selection takes effect immediately and is remembered; change it later in Settings → Basic → Display language. Existing installations keep their language and do not show the picker.
  2. (Lightweight edition only) Download the runtime: adb, the Android Emulator and the Android 14 system image. From the official source this measured 10+ MB/s, using 8 chunked connections with resumable downloads. The full and Store editions skip this step.
  3. Unpack the image for the first time: the xz image is unpacked to %APPDATA%\apkstart\system-images (about 20 seconds, done only once).
  4. Create /data for the first time: ApkStart generates its own ext4 user data with encryption and SELinux labels (the official image only contains a 1 MB placeholder).
  5. Automatic boot: after that, opening an app takes just one am start, about 23 seconds for a cold boot and about 10 seconds when a snapshot is hit.
A slow first launch is normal; it is a one-time cost. After that, apps open in seconds.

3. Everyday use

3.1 Installing apps

Pick any of three ways:

  • Double-click an APK file (register the association first: Settings → System integration → Associate .apk files);
  • choose "Install APK" in the main window;
  • on the command line: ApkStart.exe <path\to.apk>.

Split packages in .apks / .xapk format are supported (install-multiple is used automatically). After installation, desktop and Start menu shortcuts are created automatically.

3.2 Opening apps

Just double-click the desktop icon. All apps share the same runtime, so the second app starts almost instantly.

The runtime restarts (about 40 seconds, with a notice in the title bar) only the one time the "panel orientation and app orientation do not match"; afterwards, apps with the same orientation open in seconds.

3.5 File sharing (Windows ↔ Android)

The local folder %USERPROFILE%\ApkStartShared and /sdcard/ApkStartShared inside Android are synchronized in both directions within seconds. Entry point: Settings → Integration and files → File sharing (you can click "Sync now" or open the folder).

3.7 Online updates

Settings → Updates and about → Check for updates, or right-click the tray icon → Check for updates. The update path measures the sources on the spot and picks the fastest one (GitHub / Gitee / mirrors), downloads in parallel chunks and switches source automatically on failure. Updating does not remove the runtime, installed apps or snapshots.

The new portable edition supports incremental updates: every release additionally publishes a "code manifest" and a small package containing only the program code (a few MB, versus about 100 MB for the whole package). If your Electron shell version has not changed, the update downloads only this small package, verifies the files one by one and replaces the program code, which takes a few seconds. If the shell version has changed, the manifest is missing or any check fails, it automatically falls back to downloading the full package, so the program is never left broken by an update. The Store edition is still updated by the Microsoft Store.

Note: only users who install the portable edition from GitHub / Gitee through "Check for updates" get incremental updates; users who installed from the Microsoft Store use the Store channel. Incremental updates have no effect on installed apps, Android data, the runtime or snapshots.

4. Three core concepts (the key to reading errors)

Most "strange problems" come from one of the three things below. Spend a minute understanding them and troubleshooting becomes much easier.

4.1 Runtime / system image

ApkStart does not emulate an "empty Android". It loads a complete Android 14 system image as its base. 0.6.3 ships only one universal image (Google Play x86_64) that runs both x86 and ARM apps, instead of two sets ("AOSP image / compatibility image") as in older versions.

  • Image missing / damaged / incompatible with old user data → boot failure, stuck at boot, repeated restarts.
  • User data (/data) is a thin differencing layer, and one system image is shared across the whole machine.

4.2 Hardware acceleration

For the emulator to run fast it needs CPU virtualization acceleration. On Windows there are only two ways:

MethodWhat it isWho needs administrator rightsRestart required after setup?
WHPXThe built-in Windows feature "Windows Hypervisor Platform" (HypervisorPlatform)When enabling this featureYes
AEHDGoogle's own kernel driverWhen installing the driverNo

It also runs without acceleration (pure software emulation, TCG); boot just takes several minutes and the picture drops frames easily. This is "slow", not "failed to start". ApkStart falls back automatically and retries automatically with up to 4 parameter sets, in the order "rendering backend → acceleration method → memory / cold boot".

Do not mistake VirtualMachinePlatform (used by WSL2) for the acceleration switch. The emulator needs HypervisorPlatform. If only the former is enabled, emulator -accel-check still reports it as unavailable.

4.3 ARM translation layer

Most Chinese Android apps ship only ARM native libraries (arm64-v8a / armeabi-v7a), while the system image is x86_64, so a "translation layer" is needed to hand ARM instructions to the x86 CPU. The 0.6.3 universal image has the newer ndk_translation layer built in, so installing ARM apps usually needs no setup.

  • The first time an ARM app is encountered, if the translation layer component is not in place yet, ApkStart automatically fetches the compatibility image and restarts the runtime to retry (see 6.3).
  • The old image (API 30) has compatibility problems with the newer translation layer (for example ByteDance apps trigger a DoBadTrampoline SIGABRT); the Android 14 image fixes this.

5. When something goes wrong, start here: system check and automatic checks

Before you browse this manual, let the app check itself first. It can fix most problems automatically.

5.1 System check · Automatic configuration

Location: Settings → Diagnostics and repair → Start check

  • What it checks: whether CPU virtualization (VT-x/SVM) is on, whether Hyper-V / the hypervisor platform is available, graphics card / video memory / driver, memory, Windows version, emulator -accel-check, and the AEHD driver.
  • Click "Apply recommended settings" to write the safe items automatically: memory / core count / rendering resolution / picture quality / forced software emulation when there is no acceleration. They are saved as a driver for this machine that is applied automatically from then on.
  • Results are graded: ok (normal) / warn (works but optimization recommended) / bad (will not run unless handled). Each entry has a color and an explanation.

Only two kinds of things need you to act yourself:

  • BIOS virtualization: restart into the BIOS → turn on Intel VT-x / AMD SVM → Enabled (the app cannot do this step for you).
  • Windows feature / acceleration driver: see 6.1.

5.2 Automatic checks (auto debug)

Location: Settings → Diagnostics and repair → "Automatic checks · Diagnostics"

Every 10 minutes in the background it checks the machine and lists problems in six categories. Each one can be fixed in one click (restart the runtime, clear locks, clear orphan processes, invalidate the snapshot, clean up the disk, reset the Android network, and so on), and it re-checks automatically after the fix:

CategoryProblems covered
RuntimeThe real reason the last start failed, boot stuck, leftover lock files, orphan emulator processes, empty-shell snapshot, no hardware acceleration
Device connectionadb unauthorized, offline, runtime running but adb cannot see the device
StorageFree disk space, data partition configuration not matching reality, shared folder not writable
SettingsScreen orientation conflicts with the physical panel, automatic fullscreen not taking effect in a separate window
Network / logsNo network on the Android side, download source unreachable, errors in recent logs
Two principles: a failed probe is never treated as a problem (if the state cannot be obtained it reports "unknown" and never guesses), and the same old problem is not reported repeatedly.

5.3 Exporting a diagnostic report

Location: Settings → Diagnostics and repair → Export diagnostic report (or the button of the same name on the System integration page)

The report is plain text. It contains the local configuration, the automatically selected launch parameters, logs and diagnostic conclusions. Attach it when you report a problem; it speeds up locating the cause considerably.

5.4 Built-in manual and automatic tutorials

Since 0.6.3 this manual is embedded in the app: the "?" button in the main window title bar and "Open user manual (including troubleshooting)" in Settings → About both open it directly. It is searchable and scrollable, and can be printed or saved as PDF. When it opens, it jumps to the section related to the current problem.

Automatic checks and fixes also bring tutorials to you:

  • When an automatic check finds a problem, the problem entry has a "Tutorial" button on its right that opens the matching section directly;
  • For hardware acceleration, install failure, ARM translation layer, adb authorization, no sound and similar problems, when the automatic fix fails, the matching tutorial opens automatically, so you do not have to look it up here;
  • The same tutorial opens automatically only once per run, so it does not keep interrupting you.
To open it manually: the ? button in the title bar. To stop the automatic pop-up temporarily, turn off notifications in the automatic checks settings; tutorials can still be opened from the "Tutorial" button on a problem entry.

6. Troubleshooting common problems

6.1 "Hardware acceleration disabled" warning / very slow boot

Symptom: Settings / diagnostics say "No hardware acceleration right now" or "Hardware acceleration unavailable"; boot takes several minutes and the picture drops frames.

First, be clear: this is usually "slow", not "will not open". ApkStart has already fallen back to software emulation. You only need to enable acceleration if you want smooth performance.

Handling by edition:

  • Installer edition / portable edition: Settings → Diagnostics and repair → System check → find "Hardware acceleration disabled" → click Fix. A UAC prompt appears once and WHPX is enabled automatically; if it cannot be enabled (the system does not support it or you answered No), the AEHD driver is installed instead.
  • Microsoft Store (MSIX) edition: Store apps cannot elevate themselves, so clicking "Fix" opens the "Turn Windows features on or off" dialog:

1. Check "Windows Hypervisor Platform" (HypervisorPlatform); 2. after confirming, restart the computer once.

You can also run this in an administrator PowerShell:

``powershell dism /online /enable-feature /featurename:HypervisorPlatform /all /norestart dism /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart ``

Two pitfalls: (1) do not enable only VirtualMachinePlatform, because it is not the acceleration the emulator needs; (2) if VT-x/SVM is not enabled in the BIOS, first enter the BIOS and turn it on as described in 5.1, otherwise enabling the Windows features is useless. If your graphics driver is more than 3 years old, update it from the manufacturer's website; ApkStart does not install drivers automatically (installing the wrong one is worse). Some old graphics cards / integrated GPUs need a compatibility profile, see Settings → Diagnostics and repair → Drivers · Compatibility profiles.

6.2 Install failed (INSTALL_FAILED_*)

Symptom: an error appears when installing an app. The message usually starts with "Install failed:" and ends with an INSTALL_* error code.

ApkStart turns the raw error into a plain-language message. Use the table below:

Error codeMeaningWhat to do
INSTALL_FAILED_NO_MATCHING_ABISThe app only ships ARM libraries, and the current image has no ARM translation layerUsually handled automatically: ApkStart switches to the compatibility image and retries. See 6.3
INSTALL_FAILED_OLDER_SDKThe app requires a newer Android versionNeeds a newer system image; the current one is Android 14 (API 34), so this is rarely triggered
INSTALL_PARSE_FAILED_NO_CERTIFICATESThe APK has no valid signatureThe APK is damaged or not a legitimate package; get the installer again
INSTALL_PARSE_FAILED_INCONSISTENT_CERTIFICATES / INSTALL_FAILED_UPDATE_INCOMPATIBLEThe signature differs from the installed versionUninstall the old version first, then install
INSTALL_FAILED_VERSION_DOWNGRADEA newer version is already installed on the deviceDowngrading over it is not possible; install a newer version or uninstall first
INSTALL_FAILED_INSUFFICIENT_STORAGENot enough disk space in the runtimeClean up the disk, or move the runtime data folder to a drive with enough space (Settings → System integration)
INSTALL_FAILED_INVALID_APKThe APK is damaged or incompleteThe download may not have finished; download it again
INSTALL_FAILED_INVALID_URIThe APK path contains special characters or Chinese charactersMove the APK to a plain English path and install again
INSTALL_FAILED_ALREADY_EXISTSAn app with the same name but a different signature already existsUninstall it first
INSTALL_FAILED_DEPRECATED_SDK_VERSIONAn app targeting a very old Android versionHandled automatically: ApkStart retries with the official bypass flag

If the raw error is something other than the ones in the table, export a diagnostic report as described in 5.3 and send it with your feedback.

6.3 System image has no ARM translation layer / ARM app will not install or crashes

Symptom: installing reports INSTALL_FAILED_NO_MATCHING_ABIS, with a message saying "this app only ships ARM native libraries... the current system image has no ARM translation layer"; or the app crashes as soon as it starts after installation, and the log shows DoBadTrampoline, libndk_translation, UnsatisfiedLinkError or ...so not found.

Background: 0.6.3 supports both x86 and ARM with one universal Android 14 image, and the translation layer is already built in. Older versions required switching images manually; the "Universal compatibility image (managed automatically)" switch is now kept only for compatibility with old configurations and normally needs no manual change.

What ApkStart does automatically:

  1. If installing reports NO_MATCHING_ABIS, it switches to the compatibility image automatically → restarts the runtime → restores the installed apps from the local APK backups → installs again (see "Switching to the compatibility image and restarting the runtime…" in the log).
  2. If an app crashes at startup and the log clearly points to the ARM translation layer (such as DoBadTrampoline), it switches to the Android 14 compatibility image automatically and retries (log: "ARM translation layer crash detected, switching to the compatibility image automatically…").

What you need to do:

  • Be patient: switching the image restarts the runtime, which takes about 40 seconds to 1 minute each time, and you may see a notice window in the meantime.
  • Confirm the image is in place: Settings → General and installation → Runtime, check the status of "Universal compatibility image (managed automatically)"; if it shows not downloaded, click "Download compatibility image" (about 1.5 GB), and after it finishes restart the runtime for it to take effect.
  • Still crashing: a few apps have deeper anti-emulator detection (forcing checks of real sensors, baseband and so on) and cannot run in an emulator; for such apps a message is shown, and this is a limitation, not a fault.

What if you see a red "Install failed" while the message says "switching to the compatibility image automatically and retrying"?

This was a display bug in an older version: the image file was on disk, but it was reused on an old runtime that had no translation layer enabled, so the switch-and-retry was skipped and a failure was reported directly, while the message still said "retrying". You are not using the latest code; please upgrade to the latest build of 0.6.4 (the version this manual describes has this fixed: before installing, it probes the real translation capability of the current runtime instead of only checking whether the image file exists; NO_MATCHING_ABIS always triggers switch + restart + clearing the old snapshot and then reinstalls; if it still fails the second time it tells you so honestly and no longer claims to be "retrying"). After upgrading, install once more.

Tested: Hongguo Free Short Drama (com.phoenix.read, arm64-v8a only) installs normally on the Android 14 image with the new translation layer, reaches the recommendation feed and plays video. The current runtime reports ro.product.cpu.abilist = x86_64,arm64-v8a, so the translation layer is in effect.

6.4 adb unauthorized (Allow USB debugging)

Symptom: diagnostics report "Android device has not authorized debugging" (adb unauthorized), adb devices shows unauthorized, and the app never starts.

The right approach (in order):

  1. Look on screen for an emulator window showing an "Allow USB debugging?" dialog. Go to that window and click Allow, and check "Always allow from this computer" so it never asks again.
  2. If the window cannot be clicked or never appears: Settings → Runtime → Reset Android data, then retry (this removes the installed apps; the APK files are all kept and are reinstalled automatically, and the system itself is not affected).
⚠️ Do NOT delete %USERPROFILE%\.android\adbkey. Testing showed that is the opposite of what you want: Android writes a new public key only when the adb_keys file does not exist; if you swap in a new private key, the old public key stored in the system still applies, the two never match, and authorization can never succeed.
Command-line troubleshooting: ApkStart's adb server runs on dedicated port 5044 (completely separate from your own 5037): ``powershell $env:ANDROID_ADB_SERVER_PORT = 5044 adb devices # you should see emulator-5554 ` Do not manually run adb connect` against port 5555. The Play image pops up "Allow USB debugging" over the app, which looks as if the program is broken.

6.5 Double-click does nothing / endless spinner / window with a rotate button

Problems of this kind almost always point to the launch entry or window takeover. Check in the order below.

① Confirm you are using the new program

  • Look at the start of the log %APPDATA%\ApkStart\logs\app.log: start v0.6.4 is correct. If it shows v0.5.x, the desktop / Start menu shortcuts point to an old folder.
  • The old version (0.5.x) has no bundled runtime and uses the embedded window by default → "very slow + a shell window with a rotate button". Switch to 0.6.4 and point the shortcuts to the new ApkStart.exe.

② Have realistic expectations for boot time

A cold boot of about 23~48 seconds and a restart after an orientation change of about 50 seconds are the normal range. During this time clicking the icon looks like "no response", but it is actually booting in the background. Do not click several times: repeated clicks let a second instance take over the emulator, and the cleanup when the first instance exits may close the emulator too, causing failure (0.6.3 added owner.pid protection, but waiting in the queue still looks like no response). Click once and wait for it to come up.

③ Native window not taken over → falls back to the embedded window with a rotate button

If the log shows attach failed or emu:0, the window agent did not find the emulator window and the program fell back to embedded mode (the shell window with a title bar and rotate button that you see).

  • This is easily triggered when launching from a directory junction / non-standard path; 0.6.3 made the agent resolve the real path before matching. If it still appears, send the log with your feedback.

④ Reset Android data (last resort)

Settings → General and installation → Reset Android data (with a second confirmation). It removes the installed apps and data but keeps the system itself; the app list is kept and apps are reinstalled automatically when opened. It applies to all kinds of "will not open" problems caused by a damaged data partition or /data failing to mount.

6.7 App has no sound / sound is very quiet

Symptom: videos and alert sounds in an Android app are completely silent; or other Windows programs have sound and only apps inside ApkStart do not.

First tell them apart: if the system itself has no sound either, fix Windows audio first; follow the steps below only if just the apps inside ApkStart are silent.

  1. Windows volume and output device: click the volume icon in the taskbar and confirm it is not muted, the volume is not 0, and the output device is the headphones / speakers you are using. Open "Volume mixer" and check whether the ApkStart / Android runtime row has been muted separately or dragged to 0.
  2. In-app volume: some apps set the media volume to 0 the first time you enter them; raise it in the app's own settings or with the Android-side volume keys. Bilibili / Douyin and similar apps may also have turned off autoplay sound inside the app.
  3. ApkStart's sound switch: Settings → Performance and resources → Android audio must be checked. Automatic checks inspect this item; if it is found turned off, it is reported in "Settings → Diagnostics and repair", and clicking "Resolve" turns it on in one click. After changing it you must restart the Android runtime once (the runtime starts with -no-audio only when both sound and microphone are off, and a change made while running does not produce sound immediately).
  4. Windows audio service: press Win+R, enter services.msc, find Windows Audio, and confirm the status is "Running" and the startup type is "Automatic". If it was disabled, right-click to start it; this is also detected and reported by the 0.6.3 automatic checks. In an administrator PowerShell you can run net start Audiosrv.
  5. Bluetooth headphones / multiple output devices: after switching to Bluetooth headphones, Windows sometimes does not move already running programs over. Disconnect and reconnect the headphones, or restart the Android runtime once.
  6. Still no sound: after "Settings → Diagnostics and repair → Export diagnostic report", send it with your feedback; the report includes the state of the sound switch and the audio service, which shows directly whether the cause is configuration, a system service or the app itself.
When an automatic fix fails, the app opens this section automatically. If you turned off automatic check notifications, you can also get here manually from the "Tutorial" button on an automatic check problem entry or the ? button in the title bar.

6.8 Store edition fails to start / 0xC0000135 (DLL failed to load)

Symptom: after opening an app it spins forever or exits immediately, and the diagnostic report shows exit code 0xC0000135 (decimal 3221225781). It is mostly seen in the version installed from the Microsoft Store.

First, correct a common misjudgment: 0xC0000135 only means "some DLL failed to load"; it does not mean that the VC++ runtime is necessarily missing, nor that antivirus necessarily deleted a file. The same exit code has three possible causes behind it, so do not keep reinstalling based on only the first one:

  1. Path restrictions of the Store (MSIX) edition: the Store edition is installed in the read-only C:\Program Files\WindowsApps\... folder. When the Android runtime starts child processes such as qemu from this folder, the child processes look for DLLs by relative path, which can be disrupted by the container's path redirection / environment isolation; if a dependency is not found, the process exits with 0xC0000135. This is specific to the Store edition and cannot be solved by reinstalling VC++.
  2. The VC++ runtime is really missing: the Android runtime (Qt6 / qemu) depends on Microsoft VC++ 2015-2022 (x64). If Settings → Diagnostics and repair clearly reports "VC++ runtime missing (x64)", that is a measured absence of the dll file, and you can click "Resolve" to install it in one click.
  3. Antivirus quarantined runtime files: if dlls in the runtime folder were quarantined / deleted, this code is also reported. Add ApkStart's installation folder and runtime data folder to the antivirus allowlist, then install again.

Troubleshoot in order:

  1. Check whether diagnostics really show a missing VC++: if Settings reports "VC++ runtime missing (x64)", click its one-click fix. After installing, restart the computer and try again. Do not reinstall just because the exit code is 0xC0000135; first confirm that this entry was actually reported.
  2. VC++ not reported but it still fails → most likely a Store edition path problem: this is currently the most likely cause. Try in turn:
  • fully quit ApkStart (tray icon → Quit) and open it again;
  • check the antivirus "controlled folder access / ransomware protection", add ApkStart to the allowlist and restart;
  • if it still does not work, use the portable edition (ApkStart-win64-portable in the Releases of the GitHub / Gitee repository) and run it from a plain English folder (such as C:\ApkStart); the portable edition is not installed under WindowsApps and avoids this restriction directly.
  1. Getting the exact name of the failing DLL (advanced): when reporting the problem, the most valuable thing is to tell the developer exactly which dll is missing. In Event Viewer → Windows Logs → Application, find the Application Error of ApkStart / emulator and read the FaultingModuleName field; or send the report together with your feedback after "Settings → Diagnostics and repair → Export diagnostic report".
  2. What if adb also crashes: if the event log also shows adb.exe reporting 0xC0000409, that is a separate, independent problem (abnormal device connection) and not the direct cause of the emulator exit. Handle startup first using 1-3 above, and describe the adb problem separately in your feedback.
This section opens automatically: when a startup failure / fix failure is judged to be a DLL-type problem, the app opens straight to here. You can also enter it manually at any time from the "Tutorial" button on an automatic check entry or the ? button in the title bar.

6.9 App cannot use the microphone / no voice calls or recording

Symptom: voice messages, calls, recording, voice scan and similar features in an app do not work, with a message such as "no microphone / recording device unavailable".

  1. ApkStart's microphone switch: Settings → Performance and resources → Microphone input (recommended) must be checked. It is on by default; if it was turned off, automatic checks report "Microphone input is turned off in Settings" in "Settings → Diagnostics and repair", and clicking "Resolve" turns it on and restarts the runtime in one click. After changing it you must restart the Android runtime once (the switch decides whether the emulator exposes a recording device to Android).
  2. Windows microphone permission: Settings → Privacy & security → Microphone, confirm that both "Let apps access your microphone" and "Let desktop apps access your microphone" are on. Android runs inside a desktop app, and if this is off the system cannot provide the microphone at all.
  3. Confirm Windows can record: record a clip with the built-in "Sound Recorder" and confirm the microphone itself and the input device (headset microphone / webcam microphone / standalone microphone) work properly and are not muted.
  4. Select the right input device: if several microphones are plugged in, set the one you want as the default device in Windows "Sound settings → Input"; the emulator uses the system default input device.
  5. How sound and microphone relate: only when both "Android audio" and "Microphone input" are off does the emulator shut down the audio subsystem completely to save CPU; as long as one of them is on, the other keeps working normally.
When the microphone is turned off, the app side simply "cannot find a recording device" and there is no obvious error. Automatic checks are responsible for reporting this to you proactively; you can also enter this section manually from the ? button in the title bar.

6.10 Dedicated / integrated GPU rendering (graphics preference)

Symptom: the computer clearly has a dedicated graphics card, but the app picture stutters and drops frames; or a laptop gets hot and drains power, and you want to use the integrated GPU to save power.

ApkStart's Android picture uses -gpu host for hardware rendering, which really uses the computer's graphics card. Since 0.6.4 all graphics cards (NVIDIA / AMD / Intel) prefer host by default, instead of dropping AMD/Intel to software rendering across the board as old versions did, which amounted to giving up the graphics card on purpose. If host crashes on this machine, it automatically downgrades to a software backend without affecting use.

Choosing which graphics card to use: when the computer has both a dedicated and an integrated GPU, Windows sometimes assigns the emulator to the integrated one. Settings → Performance and resources → Graphics preference (dedicated / integrated) lets you specify this explicitly:

OptionSuited for
System default (recommended)Let Windows choose by power / load; the least hassle on most machines
Prefer dedicated GPUGames, video, anything needing high frame rates; uses more power and runs hotter
Prefer integrated GPULight apps, idling, saving laptop power; somewhat lower performance
  • This setting takes effect on the emulator process through the Windows "Graphics performance preference" (UserGpuPreferences), and is effective only on Windows 10 1803 and later; older systems ignore it automatically and startup is not affected.
  • After you choose, it takes effect the next time the Android runtime starts; the settings page shows whether it is currently in effect.
  • On old AMD drivers host occasionally crashes: update the graphics driver; if that still does not help, enable the bundled AMD integrated GPU swangle sample profile in "Settings → Diagnostics and repair → Drivers · Compatibility profiles" to pin rendering to a more stable backend.

6.11 Interface language (multilingual)

ApkStart supports Chinese / English / Russian / Vietnamese / Spanish / Portuguese / Japanese / Korean, plus automatic selection from the system language.

  • First launch: new installations show a language picker. Your selection takes effect immediately; existing installations keep their language without showing the picker.
  • Switch at any time: Settings → Basic → Display language. The interface is translated immediately, without restarting or interrupting running apps.
  • Follow system: automatically matches the Windows display language; unsupported languages use English.
  • The interface language affects ApkStart windows, settings and notifications. The Android system language is configured separately in Settings → Runtime and environment → System language. This manual is available in Chinese and English; some low-level diagnostic output is still Chinese. Missing source-text translations fall back to Chinese without changing functionality.

6.12 Use your own system image

ApkStart prepares its default image automatically. If you already downloaded an Android system image from an official source or copied one from another Android emulator, ApkStart can use it without downloading it again:

  1. Prepare a directory containing system.img and kernel-ranchu (or kernel). An Android SDK system-images\android-XX\tag\abi\ directory already has this structure.
  2. Settings → Performance and resources → Custom system image directory: click the directory picker or enter the path manually.
  3. The selected image is preferred after saving, starting with the next Android runtime launch. Settings indicates whether the directory is valid and highlights missing files.
  4. Clear the field to restore the bundled image.
Note: custom images must be compatible with x86_64. Changing the image changes the system: installed apps and saved data may be incompatible. Data is rebuilt automatically on first launch, and apps must be reinstalled.

9. Getting help and giving feedback

When reporting a problem, please attach these three things; they speed up locating the cause considerably:

  1. Diagnostic report: Settings → Diagnostics and repair → Export diagnostic report;
  2. The last 20 lines of app.log: %APPDATA%\ApkStart\logs\app.log;
  3. Your version and edition: for example "Store edition 0.6.4" or "Full portable edition 0.6.4".
